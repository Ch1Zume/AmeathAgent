## 0. 本次规划的依据与边界

本次目标是为已有 Ameath 桌宠增量补齐 Agent 能力，而不是另起一个桌宠项目。重点是：能在明确授权下参与游戏、准确记住共同经历、适时主动交流，并保持现有人设与交互兼容。

本次已读取 `ameath-persona.json` 的可检索内容，以及 `ameath-persona-reference.json`、`ameath-persona-guide.txt`；核验了 Neuro SDK 的官方协议、最佳实践、Randy 测试工具和 `neuro-sts2` 说明。没有取得可确认属于本项目的完整源码、实际运行环境或既有架构文档。因此，本文不声称某项程序功能已经实现或一定尚未实现，也不将此前讨论过的技术选型当作事实。

执行前必须先补齐“源码路径—现有接口—测试方式”映射。已有模块优先复用或包装；只有确认缺失后才新建。本文的模块名是逻辑职责，不是已存在的类名、文件路径或新微服务。

## 1. 定下来的五个重点方向

| 方向 | 优先级 | 用户可见的阶段成果 | 首版边界 |
| --- | --- | --- | --- |
| A. 统一事件、权限与取消机制 | P0：最小公共基础 | 聊天、游戏和观察不互相抢话；暂停与接管立即生效 | 在现有应用内增加薄协调层，不先造通用 Agent 平台 |
| B. Neuro 协议卡牌游戏接入 | P0：首个功能闭环 | 爱弥斯能在一个已支持的卡牌游戏中完成决策、执行与结果解释 | 一款游戏、一个活动会话；先保证可靠操作，不先追求高手胜率 |
| C. 可追溯的分层记忆 | P0：最小版；P1：检索完善 | 重启后能准确回忆真实共同经历，并能纠错和删除 | 先结构化事实与事件；暂不上复杂向量服务、知识图谱或自动训练 |
| D. 可控的主动陪伴 | P1 | 在授权的 PPT、论文和游戏场景适时出现，同时能真正保持安静 | 先单应用、单事件；先记录候选建议，再开放实际发言 |
| E. 低延迟语音与角色表现 | P1；新渲染能力 P2 | 用户能打断她；语音、文字与动作一致，不播放过期回复 | 保留现有渲染与动作资源；没有语音时仍可用文字完成核心流程 |

**第一版完成定义：一款游戏的可靠决策闭环 + 最小真实经历记忆 + 随时暂停和人工接管。**

读屏、完整语音和更丰富动画不是这个版本的前置条件。共同基础只实现支撑该闭环所需的部分，不以“架构重构完成”替代可体验成果。

## 2. 总体组织方式

沿用现有聊天入口、模型调用、UI 和动作播放器。在它们之间增加最小的事件协调逻辑：

```text
用户输入 / 已授权桌面事件 / 游戏 Mod
                ↓
输入适配 → 事件新鲜度与权限检查 → 当前任务协调
                ↓
当前状态 + 所需记忆 + 少量人设场景 → 决策
                ↓
          动作校验与执行
                ↓
          结果与状态确认
           ↙          ↘
真实事件记忆             角色表达 → 文字 / 语音 / 现有动作
```

游戏接口负责“能做什么”，决策层负责“选择做什么”，角色表达负责“怎样说出来”。三者不必使用三个模型，也不必拆成三个进程。首版可共用同一个模型适配器，以不同请求职责和输出校验实现分离。

人设、文档、网页和游戏描述均不能直接触发任意系统命令。工具权限由应用维护，游戏仅获得游戏动作，不获得文件、邮箱或桌面全局控制权限。

## 3. 方向 A：最小事件与权限基础

### 初步方案

建立一份内部事件记录，建议包含：`event_id`、`source`、`session_id`、`occurred_at`、`received_at`、`kind`、`task_id`、`state_revision`、`expires_at`、`payload`、`evidence_ref`。这些是 Ameath 内部字段，不要求现有 Neuro Mod 在线上协议中发送额外字段。无法从上游取得的状态版本，可以先用本地接收序号表示，但不能把它当作游戏权威版本。

协调层先做四件事：判断是否有权限、丢弃过期或重复事件、控制一个任务内的在途动作、取消已经失效的模型和输出任务。首版优先使用现有进程内队列和取消机制；没有证据表明需要消息中间件或多 Agent 框架。

权限至少分开管理：屏幕观察、发送画面到云端、保存长期记忆、游戏自动操作、麦克风监听。启用某一项不隐含启用其他项。提供能随时查看和撤销的入口。

“安静一点”停止主动闲聊或当前播报，但不自动取消用户仍要求完成的任务；“停止操作/我来玩”立即撤销游戏执行权；“停止观察”停止新的采集；“取消任务”停止对应任务。含糊的全局“停下”优先中止当前输出和会产生副作用的新操作，再通过界面显示暂停状态。

所有模型响应、工具请求和语音分片都绑定任务/轮次标识。旧任务晚到的结果可以进入诊断记录，但不得重新发声、执行动作或覆盖新状态。

### 验收

停止或接管后不再产生新的游戏动作；新问题到来后不会播报旧回答；同一个事件不会重复触发建议。工具失败时界面和台词都不能声称成功。运行日志能够解释“为什么说话、为什么保持安静、为什么执行或拒绝动作”。

## 4. 方向 B：接入 Neuro 协议的卡牌游戏

### 复用什么、不复用什么

Neuro SDK 提供游戏与 AI 之间的协议和游戏侧 SDK，不提供可直接移植的 Neuro 私有大脑或长期记忆实现。Ameath 需要承担兼容服务端的职责；不能把普通模型 API 地址直接填进游戏 Mod。[N1][N2]

第一候选是官方 `VedalAI/neuro-sts2`。其 README 明确支持以 `NEURO_SDK_WS_URL` 指向 WebSocket 服务端；构建需要 .NET 9 和本地游戏相关 DLL。它仍需在用户实际游戏版本中验证，不能因仓库存在便标记“已兼容”。[N4]

协议联调可先利用 Randy 验证游戏侧连接；Randy 是随机动作的模拟服务端，不是可与 Ameath 服务端直接对接的游戏客户端，也不覆盖所有异常行为。[N3]

### 首版实现路径

**先适配通信，再接模型，最后接真实游戏。**

1. 从现有项目中找出模型请求与配置入口，为游戏适配层复用同一个模型客户端。协议层只管理游戏连接、当前动作集合与待决请求，不承担人设、数据库和渲染职责。
2. 以官方规范建立兼容测试，覆盖 `startup`、`context`、动作注册/撤销、`actions/force`、`action` 和 `action/result`。特别测试 `action.data` 的 JSON 字符串形式；避免误发为嵌套对象。[N2]
3. 编写可回放的模拟游戏客户端：固定状态输入、固定合法动作、预期结果。先用确定性策略打通收发，再换成模型决策。禁止依赖随机模型输出验证协议正确性。
4. 真正接入游戏时，只给决策模型当前可用信息、规则摘要和可调用动作。合法性以游戏验证为准；模型不得自行编造动作名、卡牌 ID 或目标。不要为了方便给她玩家不可见的隐藏信息。[N5]
5. 先做“建议模式”：只展示拟执行动作；再开放用户明确开启的“自动操作模式”。停止按钮始终绕过模型，直接阻断后续执行。

### 可靠性设计

MVP 只允许一个活动游戏会话和一个在途动作；等待结果时不继续出下一张牌。重连、游戏重开或用户接管后，作废旧的待决请求，并根据新握手和最新状态重建可用动作集合。

对动作参数进行本地结构校验；每次发送前再确认当前会话、动作注册状态、授权与输入是否仍有效。真正执行时由游戏再次检查，避免“生成时合法，执行时已过期”。初期不为了统一抽象擅自改写原 Mod 动作名称。

失败后仅在确认未执行、仍是同一决策点且动作仍合法时，允许有上限的重新规划。**执行结果不明时暂停并重新同步，不能盲目重发会改变游戏状态的动作。** 单靠请求 ID 不能宣称跨断线具有端到端恰好一次执行保证。

官方协议允许校验后、实际游戏执行前返回 `action/result`。因此内部区分 `requested`、`accepted`、`observed_completed`、`failed`、`unknown`；成功回执不自动升级为“已经完成”。[N2] 胜负、造成伤害等台词和长期事件，以后续可观察状态为依据；信息不足就保留“结果待确认”。

玩法决策与人物台词分离：先产生可验证的动作选择，再按已知进展组织角色化表达。可以表达“我准备出这张牌”，但不能在游戏确认前说“已经赢了”。用户没请求时不逐动作讲解，也不因为聊天正在播放而无限拖延当前回合。

### 首版验收

模拟回放中：未知动作、无效参数、重复结果、迟到结果、断线和用户接管均不会造成重复或越权执行。真实游戏中：在一个明确记录版本的环境完成至少一场完整战斗，允许失败但不能卡在协议等待中；过程可暂停、可人工接管、能保存真实战斗摘要。该要求是未来验收目标，不是本次已验证结果。

## 5. 方向 C：可追溯的分层记忆

### 记忆与角色状态分开

| 层 | 保存内容 | 默认生命周期 |
| --- | --- | --- |
| 人设与原作资料 | 角色设定、出处、原作事实与允许使用的场景示例 | 版本化只读；普通聊天不自动改写 |
| 当前工作上下文 | 最近对话、当前游戏状态、当前任务和待执行动作 | 会话内或短期有效；随新状态替换 |
| 用户事实与偏好 | 明确表达的称呼、互动偏好和稳定任务信息 | 在授权下保存；允许修改、失效与删除 |
| 共同经历 | 有证据的游戏结果、共同完成的任务、值得延续的话题 | 选择性持久化；可追溯到事件 |
| 暂态角色状态 | 专注、轻松、兴奋、正在听或正在说 | 内存中衰减，不当作用户事实或真实情绪证明 |

Neuro 的 `ephemeral_context` 解决的是单次行动上下文保留方式，不替代长期记忆存储。[N2] Ameath 的长期记忆方案是本项目设计，不声称复刻 Neuro 未公开的实现。

### 首版存储与写入

先检查项目已有持久化方案；存在时加一层统一记忆接口，不重复引入第二套数据库。没有适合的存储时，再以本地 SQLite 作为默认候选。首版优先结构化字段、标签和简单文本检索；中文检索应单独用真实问法验收，不把“启用了全文检索”当作召回率合格。

一条记忆至少携带：内容、类别、实体/项目标签、来源事件 ID、来源类型、发生时间、保存时间、有效期、确认状态、替代关系和删除状态。`source_type` 区分 `user_explicit`、`tool_observed`、`canon`、`roleplay` 与 `inferred`；推测不允许在下一轮被自动提升为已确认事实。

保存规则由程序控制：用户明确要求记住的内容进入明确流程；自动提取需先启用，并排除密钥、验证码、私密窗口以及无关敏感内容。模型仅提出候选记忆，存储层做来源、授权、重复和冲突检查。人设示例不能被当作实际发生的共同经历。

例：游戏确认本局失败且用户说“下次再挑战”，可以保存“共同进行过这一局、结果失败、用户希望再试”。如果缺乏可验证分析，不保存“失败肯定因为某张牌出错”，避免把猜测写成历史事实。

### 检索、纠错与删除

每轮按当前任务检索，先过滤作用域、有效期、权限和已删除状态，再选少量相关事实与经历。相同模型上下文中，当前工具状态优先于旧游戏摘要；用户的新明确偏好优先于旧偏好。为历史与人设样例分别设置预算，场景参考库按现有建议只选 1–3 条，并保留其行为约束。[P2]

更新偏好时保留来源并明确替代旧值，不无限追加互相矛盾的记录。记忆整理只合并、去重和摘要，不凭空补足情节。对局“经验教训”先作为可检验假设，不自动变成永久策略。

提供“看见了什么记忆、为什么引用、修改、忘记”入口。忘记操作覆盖可检索记录、全文/向量索引、派生摘要和上下文缓存；必要时保留不含被删除内容的删除标记，避免日志重放重新生成记忆。备份保留或清理边界必须说明，不能承诺未实现的彻底擦除。

### 验收

应用重启后能准确引用一条真实经历；用户纠正后不再引用旧版本；忘记后检索、摘要和重放都不再恢复该内容。没有记录时能明确说不知道，而不是填补“共同回忆”。首版不以记忆数量为指标，先验证来源准确、可控与不误记。

## 6. 方向 D：可控的主动陪伴

### 先把“何时不说”做成确定性行为

默认不启用主动观察。区分 `manual`（只响应用户）、`companion`（低频陪伴）、`work_assist`（授权应用内建议）、`game_companion`（游戏陪看）和 `focus`（勿扰）等交互模式；具体命名应尽量沿用现有界面。

控制器按顺序检查：授权 → 来源可信 → 内容新鲜 → 当前任务相关 → 非专注/会议/高注意力操作 → 未重复且冷却结束 → 有足够可见证据。前面的确定性检查不通过，就不请求主模型，也不生成“我保持安静”的提示。

先沿用参考库中的 180 秒主动建议最小间隔作为可调试起点，不视为实测最优值。同一事件最多提示一次，忽略后不换说法追问。这个间隔不限制用户主动提问、紧急停止以及必要的已授权任务进度。[P2]

### 从三个具体触发器开始

**PPT：** 用户启用指定窗口观察，检测到可见且高置信度的文字越界/遮挡等问题，用户暂时停止输入时只给一个短建议。第一版只建议，不自动改文件。

**论文：** 用户选中内容或明确开启阅读辅助后，围绕当前段落解释。仅停留时间长不意味着看不懂；不要从操作停顿推断情绪或能力。

**游戏：** 先消费游戏接口的战斗结束、回合切换等可信事件，而不是重复读屏识别已有结构化信息。用户说“别指导”后关闭战术建议，仍可保留其允许的简短陪伴评论。

桌面观察优先使用已存在且被授权的窗口/应用接口；确需图像时，只截取授权区域并附采集时间。读取屏幕与向云模型发送截图分别授权；默认不保存连续原图、不观察敏感窗口。首版不实施全桌面高帧率持续上传。

### 验证与反馈

先运行“影子模式”：只记录会触发什么建议、证据是什么、最终为什么被抑制，不真的打断用户。用录制或构造的事件回放验证新鲜度、去重、模式切换和提示注入隔离后，再开启实际提示。

保存“有用 / 不需要 / 太频繁”的简短反馈用于调整触发器，而不是让模型据此改写人格。高风险授权不能通过学习用户习惯自行放宽。

### 验收

专注模式、过期画面、重复事件、私密窗口均不主动发言；用户明确求助时仍正常响应。每条主动建议都有可展示证据与抑制记录。识别错误或来源不清时不作肯定判断。

## 7. 方向 E：语音、打断和角色表现

先核验现有 TTS/STT 和播放器。已有语音能力时优先完善取消，不为了“实时”立即更换供应商；尚无语音时，游戏和记忆功能继续通过文字交付。

建议由单一输出协调器管理文字、语音队列和动画。每条输出携带 `turn_id`/`utterance_id`；只有当前有效轮次可以继续播放。用户新发言或停止命令到来时，停止播放、清空旧分片、取消或忽略旧生成，再处理新内容。不得只停 UI 动画而让后台音频继续播放。

接入麦克风后再考虑 VAD、流式转写和分句合成，并检查回声误触发。监听状态必须可见、可关闭。是否使用未完成转写做打断判断，与是否把转写当成完整用户指令分开处理。

角色状态先使用 `idle`、`listening`、`thinking`、`speaking`、`paused` 等内部状态，映射到真实可用资源。内部状态不是直接发给旧渲染器的新动作枚举。继续遵守 `playful` 的飞行限定，并对不存在的动作安全回退。[P1][P2]

语音完成应以实际播放器结束为准，而不是 LLM 文本生成结束。对接游戏侧语音通知时，按协议映射完成或取消状态。[N2] 叙述长任务时限制单段长度，让用户容易插话，但不通过省略关键结论来掩盖延迟。

### 验收

被打断后无旧音频回流、无双重播放、无已取消任务的旧字幕；网络失败可回退文字。动作不违背当前台词或用户要求。首版保留现有形象，不将 Live2D、3D、歌唱或新资产制作设为依赖。

## 8. 实施顺序与里程碑

| 里程碑 | 交付物 | 完成条件 |
| --- | --- | --- |
| M0：代码基线对齐 | 现有模块与接口清单、启动方法、最小回归结果 | 所有“已实现”判断有代码路径或运行证据；七字段配置和旧动作映射未被破坏 |
| M1：最小公共基础 | 事件/权限/取消薄层、游戏协议回放、记忆存取接口 | 不接真实游戏也能验证动作与错误处理；存储可重启恢复、可删除 |
| M2：首个可玩闭环 | 一款卡牌游戏 + 模型决策 + 文字角色回应 + 真实经历摘要 | 完成一场完整战斗；暂停/接管可靠；不把接受回执当作完成 |
| M3：可控主动陪伴 | PPT/论文/游戏的有限触发器、记忆检索、反馈入口 | 影子模式验证通过后才实际提示；专注与隐私场景保持安静 |
| M4：实时表达完善 | 可打断语音、输出状态机、现有动作联动 | 无过期播放和动作误触发；故障有文字回退 |

M0 后可以并行推进游戏协议与最小记忆两条支线，但不能同时开启多游戏、全桌面控制、新渲染器和复杂记忆平台。每个里程碑须有独立演示与回退开关。

## 9. 评估方法与完成标准

下表是拟定验收方式，不是现有系统的实测成绩。首轮先记录延迟和费用基线，再决定具体目标，避免承诺未经测试的毫秒数或胜率。

| 维度 | 首轮检查 |
| --- | --- |
| 游戏正确性 | 首次动作合法率、最终成功处理率分开统计；重试不能掩盖初次错误 |
| 副作用安全 | 停止/接管、断线和重复消息测试中，不产生重复或未授权动作 |
| 结果可信度 | 台词与记忆仅陈述真实确认结果；保留不确定状态 |
| 记忆质量 | 真实经历、纠错、遗忘、来源混淆四类用例；删除内容不能被摘要恢复 |
| 主动交互 | 统计有效建议与误打扰；专注、私密、过期、重复用例不得触发 |
| 人设兼容 | 从现有 140 条/12 组素材提取回归断言，避免只做逐字输出匹配 |
| 性能与成本 | 分开记录感知→决策、决策→执行确认、输入结束→首个有效输出的 p50/p95；统计每回合/每小时模型用量 |
| 故障恢复 | 模型超时、游戏重连、数据库失败和 TTS 失败都有明确降级，不伪造成功 |

## 10. 本阶段明确不做

不整体迁移到 AIRI，不预设采用 Electron/Tauri/Live2D 等新框架；不把所有历史对话和全部场景库塞进每次提示；不对未验证的每一条对局推测做“自我学习”；不加入未经授权的全桌面操作；不把通用多 Agent 编排、复杂向量基础设施或竞技水平作为首版门槛。

AIRI 可作为模块边界与记忆接口的设计参考。其 Alaya 相关来源在本次核验时仍以 proposal 议题呈现；这不是可以直接依赖为成品模块的证明，也不能据此断言该项目的其他记忆能力都没有实现。[N6] 任何实际借用都要先固定版本，核验相应代码、许可证和最小运行样例。
